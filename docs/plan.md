# Hub Kit plan

One package that powers all Hub projects (Stäy, Immonetz, Eiffler, Mayestate, Living Immo,
and any new one). Build a page once here, turn it on per project.

## Goal

- A project installs the kit with `npm install hub-kit@x.y.z` from GitHub Packages.
- A project file called `hub.config.ts` says which pages are on, at which URL paths,
  with which theme and brand.
- Adding a page to a project = add one line to its config, run `hub-kit sync`, done.
- A fix made here ships to every project by bumping the version. The pinned version is
  the per-project switch.

## What lives where

In the kit (this repo):

| Folder | What it holds |
| --- | --- |
| `ui/` | Base building blocks: button, table, dialog, badge, input. Token-driven. |
| `components/` | Shared pieces: invoice badges, data table, notification bell, queue cards. |
| `pages/` | Complete pages written against adapter interfaces. |
| `adapters/` | The typed interfaces a project must implement per page. |
| `themes/` | The token contract, a base stylesheet, and ready presets per brand. |
| `i18n/` | Every translation key, with English default text. |
| `cli/` | `hub-kit sync`: reads a project's config and writes its route files. |

In each project (never in the kit):

- `hub.config.ts` — enabled pages, URL paths, theme choice, brand, feature flags.
- `adapters/` — the project's Supabase queries, implementing the kit interfaces.
- `locales/` — the project's dictionaries (German today, any language tomorrow).
- `styles.css` — the project's token values.
- `routes/` — thin files generated by `hub-kit sync`, each a few lines.

## Hard rules carried over from the audit

- The kit never imports Supabase. Schemas have drifted between projects, so data access
  stays behind adapter interfaces the projects own.
- Pages that ship in the kit need extension slots for per-project differences
  (example: Stäy has Slack settings, Immonetz is bell-only). Differences become config,
  never forks.
- URL paths are config because existing users have bookmarked the German paths.
- Database changes ship as portable SQL files that check which columns exist before
  running, like the queue KPI migration already does.

  transactions).

## Phases

### Phase 1 — prove the pipeline

Extract `ui/` plus two small kits that are already portable: notifications core and
invoice queue cards. Publish version 0.1. Install it in Stäy and Immonetz. Both must
render correctly in their own theme with no code change beyond imports.

Exit test: one visual fix in the kit reaches both projects through one version bump.

### Phase 2 — first full pages

Move three self-contained pages into `pages/` with their adapter interfaces:
Team, Notifications, Processing Log. Build the `hub-kit sync` command and `hub.config.ts`.

Exit test: a brand-new empty project gets these three working pages from config alone.

### Phase 3 — the big pages

Invoice list, invoice detail, open items, bank transactions. These are the largest files
(1,800–2,000 lines) with the most per-project drift, so their adapter contracts are
designed last, on a proven pattern.

### Phase 4 — the rest, then switch off copying

Remaining pages move over one by one. When a page lives in the kit, the copies in the
projects are deleted. Porting by copy-paste ends.

## Open decisions

1. Package scope name (`hub-kit` assumed) and which GitHub org hosts the repo.
2. Handover story: a `hub-kit eject` command that copies the kit as plain files into a
   project, for the day a client repo (Stäy) moves to the client's own GitHub.
3. The three Hubs not audited yet (Eiffler, Mayestate, Living Immo) need the same route
   diff as Stäy vs Immonetz before Phase 3 contracts are frozen.
